# CDN delivery and caching

This document explains how the Share House Portal build is prepared for Vercel's
Edge Network and how to validate that hashed assets stay immutable, are
precompressed, and are delivered over modern protocols.

## Runtime expectations

- **HTTP/2 (and HTTP/3) everywhere.** Vercel automatically terminates TLS and
  negotiates HTTP/2/HTTP/3 with clients. We explicitly advertise the protocol
  support through the `Alt-Svc` header so that browsers opportunistically reuse
  HTTP/2 connections.
- **Immutable hashed assets.** Files emitted under `/_next/static/**` and any
  filename that contains a content hash must be cached by browsers and the CDN
  for one year. We rely on immutable file names generated by Next.js and
  configure the CDN to honour that.
- **Precompressed bundles.** Client bundles are produced together with `.br`
  (Brotli) and `.gz` (Gzip) variants so that the CDN can serve the smallest
  possible payload for every user agent.

## Vercel configuration

`vercel.json` defines the cache and protocol headers that are required on top of
Vercel's defaults:

- Every request to `/_next/static/**` receives
  `Cache-Control: public, max-age=31536000, immutable` together with matching
  `CDN-Cache-Control` directives.
- Hashed assets (e.g. `asset.1234567890.js`) receive the same immutable cache
  headers, plus `Vary: Accept-Encoding` so the CDN can negotiate compressed
  variants.
- `Alt-Svc: h2=":443"; ma=86400, h3=":443"; ma=86400` is attached to hashed
  assets to encourage browsers to stay on HTTP/2/HTTP/3 for subsequent requests.

If you deploy outside of Vercel, replicate these headers within your CDN or
reverse proxy configuration.

## Build-time compression

The Next.js webpack configuration installs
[`compression-webpack-plugin`](https://github.com/webpack-contrib/compression-webpack-plugin)
for client builds. During `next build` the plugin generates `.br` and `.gz`
variants for all JavaScript, CSS, HTML and similar text assets. These files are
left alongside the original bundles in `.next/static/chunks` so that the Vercel
Edge Network can pick the optimal encoding based on the requesting client.

## Continuous verification

Two automated checks protect the configuration:

1. `scripts/verify-cdn.mjs` starts a production server locally, fetches a hashed
   bundle, and verifies the presence of immutable cache headers along with the
   Brotli/Gzip artifacts. Run it locally with:

   ```bash
   pnpm build
   pnpm run test:cdn
   ```

2. `lighthouserc.json` configures Lighthouse CI to run against the production
   server. The associated GitHub Action (`.github/workflows/cdn.yml`) performs:

   ```bash
   pnpm install --frozen-lockfile
   pnpm build
   pnpm run test:cdn
   pnpm exec lhci autorun --config=lighthouserc.json
   ```

   The workflow asserts the `uses-text-compression` audit so that Brotli/Gzip
   responses never regress.

## Manual validation in production

Once the application is deployed, you can manually confirm the headers served by
Vercel:

```bash
curl --http2 -I https://<your-domain>/_next/static/chunks/<chunk>.js
```

The response must include:

- `HTTP/2 200` (or higher protocol versions)
- `cache-control: public, max-age=31536000, immutable`
- `cdn-cache-control: public, max-age=31536000, immutable`
- `vary: Accept-Encoding`
- `content-encoding: br` (or `gzip`, depending on the client)

If any header is missing, inspect your deployment environment to ensure the
updated `vercel.json` is active and that no downstream proxy strips cache or
protocol metadata.
