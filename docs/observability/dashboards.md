# Dashboards

Dashboards provide at-a-glance visibility into application health, customer
experience, and platform reliability. The dashboards below are defined in the
chosen SaaS backend (Datadog or New Relic) but are documented here so that we
can track their intended purpose, owners, and SLO coverage.

## 1. API Golden Signals

**Owner:** Platform Engineering  \
**Tool:** Datadog / New Relic  \
**SLO Coverage:** Request success rate, latency, saturation

### Widgets

| Section | Widget | Data Source | Notes |
| --- | --- | --- | --- |
| Traffic | Timeseries – Requests per second | Metric `http.server.request_count` (OTel) | Filter by `service.name:ShareHouse.Api` |
| Errors | Query value – Error rate (%) | Derived from `http.server.request_duration` status_code dimension | Shows proportion of 5xx responses |
| Latency | Timeseries – P95 latency | Metric `http.server.request_duration` (ms) | Alert threshold 750 ms |
| Saturation | Timeseries – In-flight requests | Metric `aspnetcore-current-requests` (runtime instrumentation) | Highlights thread pool pressure |
| Logging | Log stream | CloudWatch log group `/eks/share-house/api` | Filter `level:Error` with `@requestId` |
| Traces | List of slow spans | Trace search `duration > 750ms` | Link to request profile |

### Implementation notes

- Datadog: create a timeboard using the OTLP metrics that land in the `otel.*`
  namespace. Ensure the `service` and `env` tags are mapped from the resource
  attributes sent by OpenTelemetry.
- New Relic: build a dashboard in NerdGraph referencing NRDB metrics
  `MetricTimeslice` (e.g., `metricTimeslice{name='http.server.request.duration'}{...}`).

## 2. Authentication Journey

**Owner:** Identity Team  \
**Tool:** Datadog / New Relic  \
**SLO Coverage:** Signup success rate, login latency

### Widgets

- Funnel view: `signup_started` → `signup_completed` events (traces with
  custom spans sourced from `ShareHousePortal.Identity`).
- Timeseries: `auth.login.duration` P95 vs. target 400 ms.
- Top Errors table: CloudWatch logs filtered by `eventType:Authentication` and
  `level:Error`.
- User Impact: Query traces segmented by `user.plan` attribute to show errors by
  subscription tier.

### Implementation notes

Instrumentation must add custom spans and attributes within the authentication
controller. Use `ActivitySource` from `.NET` to mark steps such as email OTP
validation and Supabase integration calls. Log bodies should include a
`metrics.auth.durationMs` field so that the CloudWatch metric filter can detect
slow authentication attempts.

## 3. Infrastructure Footprint

**Owner:** SRE  \
**Tool:** Datadog (preferred)  \
**SLO Coverage:** Node saturation, collector health

### Widgets

- Collector CPU / Memory utilisation from the
  `otelcol_process_memory_rss` and `otelcol_process_cpu_seconds_total` metrics.
- Kubernetes DaemonSet status for the Fluent Bit / FireLens agents that forward
  logs (if present).
- CloudWatch alarm status summary (import alarms generated by Terraform module).
- Heat map of API pods by error rate (trace spans aggregated by `k8s.pod.name`).

## Dashboard version control

For Datadog, export dashboards as JSON definitions and store them under
`docs/observability/dashboards/` when available. For New Relic, commit the NerdGraph
queries required to re-create each widget. Until automation is in place, this
file acts as the source of truth for expected visualisations.
